# Подключение клиентов

[English](../en/client-setup.md) | **Русский** · [Оглавление](README.md)

## Требования к публикации сервиса

- **`PECL_PROXY_PUBLIC_URL`** — адрес, по которому клиенты ходят к прокси. Он попадает в
  `channel.xml` и в ссылки на архивы.
- **Порт 80 (HTTP) или 443 (HTTPS)**. Нестандартный порт (`http://host:8080`) работает только
  при доступном pecl.php.net. Причина — в разделе про особенности PEAR ниже.
- Имя хоста из букв, цифр, точек и дефисов (так PEAR проверяет имена серверов канала).

`docker-compose.yml` из репозитория публикует контейнер на порту 80. Пример с HTTPS —
[`deploy/nginx.conf.example`](../../deploy/nginx.conf.example).

## Подключение

Один раз на машине или в образе:

```sh
pecl channel-update http://pecl-proxy.example.local/channel.xml
pecl config-set preferred_mirror pecl-proxy.example.local
```

- `channel-update` скачивает `channel.xml` с прокси и записывает в реестр канала pecl.php.net
  адреса REST прокси. Все последующие запросы к каналу, включая зависимости вида
  `pecl_http → raphf`, идут через прокси.
- `preferred_mirror` направляет на прокси проверку `channel.xml`, которую pecl делает перед
  каждой установкой (подробности ниже).

Готовые команды с правильным адресом есть на главной странице прокси.

Проверка:

```sh
pecl channel-info pecl.php.net
# REST BASE и MIRROR должны указывать на http://pecl-proxy.example.local/rest/
pecl config-get preferred_mirror
```

Дальше всё как обычно:

```sh
pecl install redis
pecl install redis-6.3.0
pecl install apcu-beta
```

### Dockerfile

```dockerfile
FROM php:8.3-cli
RUN pecl channel-update http://pecl-proxy.example.local/channel.xml \
 && pecl config-set preferred_mirror pecl-proxy.example.local \
 && pecl install redis-6.3.0 apcu-5.1.28 \
 && docker-php-ext-enable redis apcu
```

В сборках, которые должны быть воспроизводимыми, **указывайте версии явно**. Без версии
клиент выбирает самый свежий подходящий релиз: при доступном pecl.php.net — самый свежий там
(он попадёт в кеш), без него — самый свежий в кеше прокси. Один и тот же Dockerfile может
поставить разные версии с интернетом и без.

### Отключение

```sh
pecl config-set preferred_mirror pecl.php.net
pecl channel-update pecl.php.net        # нужен доступ к pecl.php.net
```

## Стабильные и нестабильные релизы

У каждого релиза на pecl.php.net есть стабильность: `stable`, `beta`, `alpha` или `devel`.
Прокси кеширует и отдаёт их одинаково, а какой релиз взять, решает клиент:

- `pecl install <пакет>` берёт самый свежий релиз не менее стабильный, чем `preferred_state`
  (по умолчанию `stable`; меняется командой `pecl config-set preferred_state beta`);
- `<пакет>-beta`, `-alpha`, `-devel` ослабляют это требование для одной команды;
- `<пакет>-<версия>` ставит именно эту версию, независимо от стабильности.

Главная страница помечает нестабильные версии в кеше, а `GET /_admin/packages` и
`pecl-proxy list` показывают стабильность каждой закешированной версии
([admin-api.md](admin-api.md)).

## Что работает без интернета

- Любая версия, которую хоть раз скачивали через прокси, вместе с её PECL-зависимостями.
  При скачивании архива прокси сам докачивает метаданные этой версии.
- `pecl install <пакет>` без версии — самый свежий закешированный релиз, подходящий под
  `preferred_state`. Если в кеше только нестабильные версии, pecl так и сообщит («latest
  release is version 0.1.0, stability beta»); поставить их можно через `<пакет>-beta` или
  явную версию.
- Пакеты и версии, которые никогда не запрашивались, недоступны (ошибка «No releases
  available» / 504). Заполнить кеш заранее можно командой `pecl-proxy warm`
  ([operations.md](operations.md#прогрев-кеша)).

## Команды pecl и что они запрашивают

Все команды, работающие с каналом, идут через прокси, включая проверочную `channel.xml`
благодаря `preferred_mirror`. Прокси кеширует ровно то, что запросил клиент. У команд,
показывающих информацию, это метаданные без архивов, иногда очень много файлов:

| Команда | Запросы клиента | Без интернета |
|---|---|---|
| `install`, `download`, `upgrade` | `r/<pkg>/allreleases.xml`, `p/<pkg>/info.xml`, `r/<pkg>/<v>.xml`, `r/<pkg>/deps.<v>.txt`, архив `get/<pkg>-<v>.tgz`; то же для обязательных зависимостей | Версии, которые уже скачивались через прокси; без версии — самая свежая из них. |
| `remote-info <pkg>` | `p/<pkg>/info.xml`, `r/<pkg>/allreleases.xml`, затем `deps.<v>.txt` и `<v>.xml` **каждого** релиза пакета. У `pecl_http` 160 релизов, поэтому первый вызов — 322 запроса, все промахи кеша по очереди уходят в pecl.php.net. Повторные вызовы обслуживаются из кеша. | Только закешированные версии; `Latest` — самая свежая из них. |
| `remote-list`, `list-all` | `c/categories.xml`, затем `c/<категория>/packagesinfo.xml` для каждой из ~50 категорий pecl (несколько МБ — сведения обо всех пакетах канала) | Собирается из кеша: только пакеты с архивами в кеше и только их закешированные версии. |
| `search <строка>` | `p/packages.xml`, затем `p/<pkg>/info.xml` и `r/<pkg>/allreleases.xml` каждого пакета, в имени которого есть строка. При поиске по описанию (`search <строка> <описание>`) — `info.xml` всех пакетов канала. | Ищет только среди пакетов с архивами в кеше (`p/packages.xml` собирается из кеша). |
| `list-upgrades`, `upgrade-all` | `p/packages.xml`, `r/<pkg>/allreleases.xml` установленных пакетов и `<v>.xml` найденной новой версии | Пакеты с архивами в кеше; последней считается самая свежая закешированная версия. |

Пока upstream доступен, все эти команды идут через прокси и кешируются, как и всё остальное;
ответы без upstream описаны в [operations.md](operations.md#недоступность-upstream). Списки
и `allreleases.xml` обновляются по `METADATA_TTL`. Файлы конкретных версий хранятся
бессрочно и перепроверяются heartbeat'ом ([operations.md](operations.md#что-и-как-кешируется)).
Кроме того, PEAR-клиент держит собственный кеш REST-ответов (`cache_dir`, `cache_ttl`
по умолчанию 3600 с), поэтому в течение часа повторные вызовы на той же машине могут вообще
не доходить до прокси.

## Особенности PEAR-клиента

Найдены при разработке по исходникам [pear/pear-core](https://github.com/pear/pear-core)
(PEAR 1.10.x — та же версия, что в официальных образах `php:*`). Проверены end-to-end тестом
с настоящим клиентом.

### `Host` без порта

`PEAR/REST.php` и `PEAR/Downloader.php` отправляют `Host: <хост>` без порта. Если прокси
доступен на нестандартном порту и `PUBLIC_URL` не задан, адреса в `channel.xml` получатся без
порта, и клиент пойдёт на порт 80. Поэтому `PUBLIC_URL` нужно задавать; без него сервис
пишет предупреждение при старте.

### Проверка channel.xml перед каждой установкой

Перед `install`/`download` клиент запрашивает `http://<preferred_mirror>/channel.xml`, а при
ошибке — `https://...` (`PEAR/Downloader.php`, метод `download`). По умолчанию
`preferred_mirror` равен имени канала, то есть запрос идёт на **pecl.php.net** напрямую, мимо
прокси. Из-за ошибки в обработке ошибок PEAR неудача обеих попыток не игнорируется, а
**завершает команду**. Без интернета `pecl install` падает, даже если всё нужное лежит в
кеше прокси.

Решение: прокси указывает себя зеркалом канала в отдаваемом `channel.xml`
(`<mirror host="pecl-proxy.example.local">`), а клиент выбирает это зеркало через
`config-set preferred_mirror`. Тогда проверка идёт на прокси и получает 304.

URL этой проверки PEAR собирает **без порта**, поэтому сервис должен быть доступен на 80/443.
Если `PUBLIC_URL` указывает на другой порт, прокси не добавляет себя зеркалом и пишет
предупреждение при старте.

### Прямая проверка канала в remote-info, remote-list, search

`remote-info`, `remote-list`, `list-all`, `search` и `list-upgrades` начинают с
`_checkChannelForStatus()` (`PEAR/Command/Remote.php`), которая запрашивает
`http://pecl.php.net/channel.xml` **напрямую**: `preferred_mirror` она игнорирует (переменную
читает, но не использует), прокси тоже. Ошибки при этом игнорируются, и команды работают, но в
закрытой сети, где пакеты к pecl.php.net отбрасываются, клиент каждый раз ждёт
`default_socket_timeout` PHP (60 с). Прокси этот запрос не видит.

Решение для изолированной сети: пусть `pecl.php.net` указывает на прокси. Он отвечает на
`/channel.xml` для любого имени хоста; слушать нужно порт 80 этого адреса.

```sh
docker build --add-host pecl.php.net:10.0.0.5 .        # 10.0.0.5 — адрес прокси
docker run --add-host pecl.php.net:10.0.0.5 ...
# docker-compose: extra_hosts: ["pecl.php.net:10.0.0.5"]
# хост или ВМ: "10.0.0.5 pecl.php.net" в /etc/hosts или запись в DNS
```

`install` и `download` такого запроса не делают, им достаточно `preferred_mirror`.

### Зеркало указано дважды

`PEAR_Registry::_mirrorExists()`, которую вызывает `config-set preferred_mirror`, перебирает
элементы `<mirror>` как список. Единственное зеркало парсер возвращает не списком, поэтому
команда отвечает «Channel Mirror ... does not exist». Прокси указывает себя зеркалом дважды;
на работу клиента это не влияет.

### `update-channels` возвращает оригинальный канал

`pecl update-channels` и `pecl channel-update pecl.php.net` скачивают `channel.xml` с
настоящего pecl.php.net (если он доступен) и затирают адреса прокси. После них повторите
команды подключения. Без интернета эти команды ничего не меняют.

### Почему канал называется pecl.php.net

Скачав архив, клиент сверяет канал из `package.xml` внутри архива с каналом, из которого
ставит пакет, и при расхождении прерывает установку: `CRITICAL ERROR: We are
<канал>/redis-6.3.0, but the file downloaded claims to be pecl.php.net/redis-6.3.0`.
Отдельное имя канала потребовало бы перепаковывать каждый архив. Поэтому канал остаётся
`pecl.php.net`, а на прокси указывают только его адреса — архивы при этом совпадают с
оригиналом байт-в-байт.
